# 1. Expo CNG: no committed `ios/` and `android/` directories

- **Status:** Accepted
- **Date:** 2026-09-05

## Context

A React Native app either keeps generated Xcode and Gradle projects in git
("bare") or regenerates them from the JS config (Expo Continuous Native
Generation). Committed native projects rot: they collect hand edits no config
describes, they conflict on every upgrade, and an SDK bump becomes a multi-day
merge. The cost of CNG is that native changes need a plugin, not an Xcode edit.

## Decision

The template uses CNG. `ios/` and `android/` are generated by `expo prebuild
--clean --no-install` and gitignored; everything native is config, a config
plugin, or a local Expo Module.

- `.gitignore` — `/ios`, `/android`.
- `app.config.ts` — the single source for identifiers, icons and plugins.
- `plugins/with-build-stamp.ts`, `with-android-release-signing.ts`,
  `with-android-release-abis.ts` — native changes as tested code.
- `modules/hello-native/` — the local-module path, Swift and Kotlin.
- `scripts/check-prebuild.sh` (`make check-prebuild`) — prebuilds into a temp
  dir and greps the plugin output, so plugin drift fails a check, not a build.

## Consequences

Upgrades are a dependency bump plus a prebuild. Nothing native can be fixed by
editing the generated project: the next prebuild erases it, and `make prebuild`
exists only for debugging plugins. Every native capability costs a plugin or
module plus a test and a `docs/native-extensions.md` entry; CI hashes
`plugins/**` and `modules/**` into its native cache key.

## Alternatives

- **Bare workflow with committed native projects** — rejected: upgrade cost and
  untracked hand edits are what this template exists to avoid.
- **Expo Go only** — rejected: the app ships a local native module.
